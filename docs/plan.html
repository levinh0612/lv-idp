LV-IDP – Identity Provider đa năng

Một auth service dùng chung cho mọi ứng dụng: nhiều kiểu đăng nhập (local, Google, Facebook, GitHub, Keycloak/OIDC, SAML, LDAP), nhiều loại database người dùng, và authorization (RBAC → ReBAC). Tài liệu này là bản thiết kế; từng bước thực hiện nằm ở docs/days/.

1. Tổng quan & mục tiêu

Mục tiêu
  • Là OAuth2 / OIDC Provider chuẩn, app nào cũng tích hợp được bằng thư viện có sẵn.
  • Là Identity Broker: gom nhiều nguồn đăng nhập về một danh tính thống nhất.
  • Là User Federation: đọc user từ DB/LDAP có sẵn, không bắt migrate một lần.
  • Cung cấp Authorization (role, permission, policy) cho các service.
  • Multi-tenant (realm/tenant), có Admin API/UI, audit đầy đủ.
Không làm (non-goals) ở v1
  • Tự viết thuật toán mật mã / parser XML-DSig (dùng thư viện đã kiểm chứng).
  • Full SAML IdP (chỉ làm SAML upstream trước; SAML IdP ở P2).
  • Theme engine phức tạp như Keycloak.
  • Chạy cluster đa vùng (multi-region active-active).
Nguyên tắc thiết kế
  • Chuẩn trước, tự chế sau: bám RFC/OIDC để tương thích.
  • Tách bạch Authentication / Token / Authorization.
  • Mọi thứ cắm được qua SPI (provider, storage, authenticator, mapper).
  • Secure by default: PKCE bắt buộc, rotation, rate-limit.
  • Stateless ở tầng token, state ngắn hạn ở Redis, state lâu dài ở PostgreSQL.
Lưu ý trung thực: Keycloak, Zitadel, Authentik đã làm gần như đủ danh sách này. Dự án này hợp lý nếu mục đích là học sâu + kiểm soát hoàn toàn + tích hợp đặc thù (ví dụ iDempiere, DB legacy). Nếu chỉ cần chạy production nhanh, nên cân nhắc dùng Keycloak/Zitadel và chỉ viết phần SPI riêng. Hướng đề xuất: dùng Spring Authorization Server làm lõi giao thức, tự xây phần Broker, Storage SPI, MFA, Authorization ở trên nó.

Rút ra 8 pattern chung

  1. Tenant/Realm là ranh giới cô lập (issuer, key, user, client đều theo tenant).
  2. Protocol layer mỏng (OIDC/OAuth2/SAML) ↔ Authentication engine ↔ User store.
  3. Federation qua connector với interface nhỏ; mapping claim cấu hình được.
  4. Authentication = pipeline các bước (flow/stage), có điều kiện (risk, MFA).
  5. Key management riêng: rotate khóa ký, JWKS có nhiều key (kid).
  6. Refresh token rotation + reuse detection, session có thể revoke.
  7. Authorization tách khỏi Authentication; token chỉ mang claim thô (roles/scope), quyết định chi tiết hỏi policy service.
  8. Event/Audit first-class, có webhook cho hệ thống ngoài.

sequenceDiagram
  autonumber

  participant I as LV-IDP
  participant DB as Token Store

  I->>DB: find RT1 in family F
  alt RT1 is current
    I->>DB: mark RT1 used, issue RT2 in family F

7. Extensibility: các SPI chính

Chỉ giữ 5 điểm mở rộng để tránh "SPI sprawl" như Keycloak. Mỗi SPI là một interface trong idp-core, implementation đăng ký bằng Spring bean + tên type, cấu hình lưu theo tenant trong DB.

public interface FederationConnector {            // Google, GitHub, Facebook, OIDC, SAML
    String type();
    URI buildAuthorizationRequest(ConnectorContext ctx, String state, String nonce);
    ExternalIdentity handleCallback(ConnectorContext ctx, HttpServletRequest req);
}

public interface UserStorageProvider {            // Local JPA, External JDBC, LDAP
    String type();
    Optional<UserRecord> findByUsername(StorageContext ctx, String username);
    Optional<UserRecord> findByExternalId(StorageContext ctx, String id);
    boolean verifyCredential(StorageContext ctx, UserRecord u, char[] password);
    default boolean readOnly() { return true; }
}

public interface Authenticator {                  // 1 stage trong flow: password, totp, webauthn...
    String id();
    StageResult authenticate(FlowContext ctx);    // CONTINUE | CHALLENGE | FAIL
}

public interface ClaimMapper {                    // biến đổi claim upstream/nội bộ → token claim
    Map<String,Object> map(MappingContext ctx);
}

public interface EventListener {                  // audit, webhook, metrics
    void on(IdpEvent event);
}

10. Security checklist (bắt buộc)

Giao thức
  • PKCE bắt buộc cho public client; bỏ Implicit & ROPC.
  • Redirect URI so khớp chính xác (không wildcard).
  • state, nonce kiểm tra đầy đủ; validate iss, aud, exp.
  • Authorization code dùng 1 lần, TTL ≤ 60s.
  • Access token ngắn (5–15 phút), refresh rotation + reuse detection.
Credential
  • Argon2id (hoặc bcrypt cost ≥ 12), pepper tuỳ chọn.
  • So sánh constant-time; thông báo lỗi không lộ user tồn tại.
  • Rate limit theo IP + account; lockout mềm; check mật khẩu bị lộ (HIBP k-anonymity).
  • Recovery code lưu dạng hash.
Khóa & bí mật
  • Key ký RS256/ES256 theo tenant, rotate định kỳ, JWKS giữ key cũ đến khi token hết hạn.
  • Private key & client secret mã hóa at-rest.
  • Không log token, password, secret.
Web
  • Cookie HttpOnly; Secure; SameSite; CSRF cho form login.
  • CSP, X-Frame-Options (chống clickjacking trang login), HSTS.
  • CORS allow-list theo client.
  • SSRF guard khi gọi discovery/JWKS upstream (chặn IP nội bộ).
Federation
  • Account linking chỉ khi email đã verified ở upstream (chống account takeover).
  • Không tin email Facebook/GitHub chưa verify.
  • SAML: validate signature, InResponseTo, audience, NotOnOrAfter; chặn XXE.
Vận hành
  • Audit mọi sự kiện auth (thành công/thất bại).
  • Tách schema/tenant filter bắt buộc ở repository (tránh rò dữ liệu chéo tenant).
  • Test: OIDC conformance suite, OWASP ASVS L2, dependency scan.

13. Quyết định kiến trúc (ADR) & rủi ro

#Quyết địnhLý doĐánh đổi
ADR-1Modular monolith, không microservice ngayIdP cần nhất quán mạnh, ít latency; vận hành đơn giản.Tách sau cần kỷ luật ranh giới module.
ADR-2Dùng Spring Authorization Server (nay nằm trong Spring Security 7) làm lõiTránh sai sót bảo mật khi tự viết OAuth2; có sẵn DPoP, token exchange; không còn lệch version giữa SAS và Security.Phải theo cách mở rộng của framework; API đổi giữa 6.x/7.x nên đọc migration guide.
ADR-3Multi-tenant bằng cột tenant_id + issuer theo tenant (/t/{slug})Rẻ, dễ vận hành.Cần filter bắt buộc; isolation yếu hơn schema-per-tenant.
ADR-4Access token = JWT ngắn hạn; refresh = opaque, lưu hashResource server verify offline; revoke được qua refresh.Access token không revoke tức thì → TTL ngắn + introspection cho API nhạy cảm.
ADR-5Authorization tách thành service nội bộ với Check APICho phép nâng cấp RBAC → ReBAC không đổi token.Thêm 1 hop; cần cache.
ADR-6Federation qua interface FederationConnector nhỏ (kiểu Dex)Thêm provider chỉ cần 1 class + config.Provider đặc thù cần mapping riêng.

Rủi ro chính

  • Account takeover qua linking → chỉ link khi email verified, hỏi xác nhận nếu nghi ngờ.
  • Rò dữ liệu chéo tenant → tenant filter ở repository + test tự động.
  • Hash legacy yếu (MD5/SHA1) → chỉ dùng để xác minh, rehash ngay khi đăng nhập thành công.
  • Phình scope → bám đúng MVP/P1/P2; P2 chỉ làm khi MVP chạy ổn.
  • Key bị lộ/mất → backup mã hóa, quy trình rotate đã test.
